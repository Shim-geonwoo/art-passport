# Art Passport

문화예술 공연·전시를 예매하고, 관람 기록을 여권처럼 모으는 모바일 앱.

**"예매가 끝이 아니라 시작"** 이라는 문제의식에서 출발했다. 대부분의 예매 앱은 결제가 끝나면
할 일이 끝나지만, 정작 사용자에게 남는 건 그 뒤의 경험이다. Art Passport는 예매한 티켓을
**보딩패스**로 지갑에 넣어두고, 관람이 끝나면 그 포스터가 **여권 스탬프**로 찍히며,
스탬프 9개를 채우면 **할인 쿠폰**이 나온다.

> 포트폴리오·데모용 프로젝트다. 결제는 실제 PG 연동 없이 테스트 결제만 동작한다.

---

## 핵심 흐름

```
 예매하기 ──▶ 보딩패스(월렛)  ──▶  관람일이 지나면  ──▶ 여권 스탬프
                  │                                          │
              D-day 배지                                 9칸 채우면
             (3일 이내 강조)                          쿠폰 1장 (10% 할인)
                                                            │
                                              다음 예매에 적용 ─┘
```

한 건의 예매가 상태를 바꿔가며 앱 전체를 관통한다. 티켓을 사면 즉시 지갑에 들어오고,
관람 시각이 지나는 순간 지갑에서 빠지면서 여권에 스탬프가 찍힌다.
**이 전환에 배치 작업이나 크론이 하나도 없다** — 아래 "설계 노트" 참고.

## 화면

| 탭 | 하는 일 |
|---|---|
| **보딩패스** | 아직 관람 전인 티켓을 애플 월렛처럼 겹쳐 쌓는다. 카테고리별 색, QR, D-day 배지 |
| **예매** | 공연·전시 50건 카탈로그. 검색·카테고리 필터 → 상세 → 관람일/회차 선택 → 테스트 결제 |
| **여권** | 관람 완료한 공연의 포스터가 3×3 스탬프로 찍힌다. 9칸 = 1페이지 = 쿠폰 1장 |
| **마이페이지** | 예매 관리(취소 포함), 리워드(쿠폰), 프로필 편집, 설정 |

인증은 이메일/비밀번호. 비밀번호 재설정(6자리 코드), 인증메일 재발송, 회원 탈퇴까지 동작한다.

### 관리자 모드

마이페이지 안에 있고 **관리자 계정에만 메뉴가 보인다.** 카탈로그를 SQL Editor 없이 앱에서 관리한다.

| 화면 | 하는 일 |
|---|---|
| 공연 목록 | 카탈로그 전체를 관리자 시선으로. **숨긴 것까지 전부** 나오고, "지금 예매 탭에 보이는가"와 안 보인다면 그 이유(회차 없음 / 숨김 / 전시 종료)를 뱃지로 붙인다 |
| 공연 편집 | 이름·장르·장소·가격·기간·소개글·포스터. id 없이 들어가면 새 공연 등록이 되고, 그때는 회차도 함께 만든다 |
| 회차 관리 | 회차 추가·수정·삭제와 회차별 정원. 판매 수와 잔여석을 함께 보여준다 |

**삭제는 없고 "내리기"만 있다.** 예매가 달린 공연이 사라지면 이미 판 티켓의 예매 상세와 여권
스탬프가 가리킬 곳을 잃는다. DB도 같은 이유로 막아뒀다 — `events`에는 delete 정책도 권한도 주지
않았다. 내리면 **새 예매는 서버가 막고**(화면에서 감추는 것만으로는 부족하다 — 상세를 열어둔
사람은 그대로 결제까지 갈 수 있다), 이미 예매한 사람의 보딩패스·스탬프와 **취소할 권리는 그대로
남는다.**

## 설계 노트

이 프로젝트에서 가장 신경 쓴 네 가지다.

### 1. 상태를 저장하지 않고 계산한다

예매 상태(예매완료/관람완료/취소)를 컬럼에 저장하지 않는다.
저장하는 건 **`is_cancelled` 하나뿐**이고, 나머지는 조회할 때 `watched_at`과 현재 시각을 비교해
계산한다. 스탬프도 별도 테이블이 없다 — 관람일이 지난 예매를 정렬한 것이 곧 스탬프 목록이다.

덕분에 **"관람일이 지나면 스탬프로 바꿔주는" 배치 작업이 필요 없다.** 날짜가 바뀌는 순간부터
그렇게 보인다. 쿠폰 만료도 같은 방식이라(`expires_at` vs 현재 시각) 만료 처리 크론이 없다.

기준이 관람 *시각*이 아니라 *일자*(다음 날 00:00)인 이유는, 공연이 몇 시에 끝나는지를 저장하지
않기 때문이다. 시작 시각으로 끊으면 아직 공연을 보고 있는 중에 티켓이 지갑에서 사라진다.

예외는 회차별 잔여석(`sold_count`) 하나다. 클라이언트는 RLS 때문에 남의 예매를 볼 수 없어
계산할 방법이 없어서 트리거로 유지한다. 대신 **값을 더하고 빼지 않고 매번 다시 세서** 어긋날
여지를 없앴다.

### 2. 믿으면 안 되는 값은 서버가 다시 계산한다

앱은 `bookings`·`coupons`를 직접 쓰지 못한다. RLS는 조회만 열려 있고, 쓰기는 서버 함수
(`SECURITY DEFINER`)로만 한다. 클라이언트는 **"무엇을·몇 매·어떤 쿠폰으로·언제"** 만 말하고,
관람 시각·할인율·금액은 서버가 `events`/`coupons`를 다시 읽어 계산한다.

이게 중요한 이유는 1번 설계 때문이다. 상태를 `watched_at`으로 계산하므로, 클라이언트가
`watched_at`을 정할 수 있으면 **과거 시각을 적어 스탬프를 즉시 만들어낼 수 있다.**
스탬프 9개 = 쿠폰 1장이므로 그건 곧 할인 발급 권한이 된다.

| 함수 | 하는 일 |
|---|---|
| `create_booking` | 예매 생성 + 쿠폰 사용 처리 (한 트랜잭션). 회차 행을 잠그고 잔여석을 직접 세어 초과 판매를 막는다 |
| `cancel_booking` | 취소 + 썼던 쿠폰 반환 |
| `issue_due_coupons` | 스탬프 9개마다 쿠폰 발급 |
| `delete_own_account` | 회원 탈퇴 (`auth.uid()`로만 지워 남의 계정을 지목할 수 없다). 프로필 사진도 함께 지운다 — Storage는 연쇄 삭제가 안 닿는다 |

자세한 내용은 [`docs/data-structure.md`](docs/data-structure.md)에 정리돼 있다.

### 3. 파는 방식은 플래그가 아니라 데이터가 정한다

공연은 회차를 골라 사고(정원 있음), 전시는 기간 안에서 날짜를 고른다(정원 없음). 이 갈림길을
`is_exhibition` 같은 칸으로 두지 않았다. **회차가 하나라도 있으면 회차형, 없고 종료일이 있으면
기간형이다.**

```
회차 있음        →  회차를 골라 산다 (회차마다 정원)
회차 없음 + 종료일 →  기간 안에서 날짜를 고른다 (정원 없음)
둘 다 없음        →  아직 팔 수 없다
```

칸으로 뒀다면 "전시인데 회차가 있는" 모순된 조합을 만들 수 있고, 관리자는 칸과 회차를 손으로
맞춰야 한다. 이 방식에서는 **회차를 만드는 행위 자체가 파는 방식을 정하고**, 회차를 전부 지우면
기간형으로 돌아간다. 덕분에 시간지정 입장 전시(30분 단위로 인원을 끊어 받는 전시)가 별도 분기
없이 그냥 표현된다.

대신 판단 순서가 네 곳에 흩어져 있어서(서버 함수, 예매 가능 여부, 관리자 뱃지, 결제 화면)
**넷이 같은 순서로 갈라야 한다.** 하나라도 어긋나면 화면이 "예매 가능"이라고 한 것을 서버가
거절하고, 누른 사람은 앱이 고장 난 줄 알게 된다. 그래서 이 규칙만 따로 테스트로 못박아뒀다.

### 4. 관리자 표시는 사용자가 손댈 수 없는 곳에 둔다

가장 손쉬운 방법은 `users`에 `is_admin` 칸을 붙이는 것이다. 그런데 이 프로젝트에는 사용자가
자기 프로필 행을 직접 수정하는 정책이 이미 있다(닉네임·프로필 사진을 그렇게 바꾼다). 거기에
`is_admin`이 있으면 **누구나 자기를 관리자로 승격시킬 수 있다.**

그래서 관리자 표시는 별도 표(`admins`)에 두고 두 겹으로 막았다. 앱이 쓰는 역할에서 권한을
회수하고(`revoke all`), RLS를 켜되 정책을 **하나도 만들지 않았다.** 이 표를 읽는 경로는
`is_admin()` 함수 하나뿐이다(`SECURITY DEFINER`라 표 주인 자격으로 돈다).

카탈로그 쓰기는 예매·쿠폰과 달리 서버 함수가 아니라 RLS 정책으로 막는다. 예매는 클라이언트가
보낸 금액·시각을 믿으면 안 되어서 서버가 다시 계산해야 하지만, **공연 등록은 관리자가 곧 정보의
출처라 서버가 다시 계산할 원본이 없다.** 확인할 것은 "누가 하느냐" 하나뿐이고 그건 정책이 하는
일이다. 함수로 감싸면 칸 수만큼 인자를 늘어놓은 껍데기가 될 뿐이다.

앱에서 메뉴를 감추는 건 편의일 뿐이다. 관리자가 아닌 사람이 관리 화면에 들어와도 목록은
보이지만(누구나 볼 수 있는 카탈로그다) 무언가를 저장하려 하면 서버가 거절한다.

## 로컬에서 실행하기

### 1. 의존성 설치

```bash
npm install
```

### 2. Supabase 프로젝트 연결

[supabase.com](https://supabase.com)에서 프로젝트를 만든 뒤, `.env.example`을 복사해 `.env`를 만들고
값을 채운다. (`.env`는 커밋되지 않는다)

```bash
cp .env.example .env
```

```
EXPO_PUBLIC_SUPABASE_URL=https://your-project-ref.supabase.co
EXPO_PUBLIC_SUPABASE_ANON_KEY=your-anon-public-key
```

### 3. 데이터베이스 준비

마이그레이션 19개를 적용한다. 스키마·RLS·서버 함수·Storage 버킷과 함께
**공연·전시 50건이 시드로 들어간다.**

```bash
npx supabase link --project-ref <your-project-ref>
npx supabase db push
```

비밀번호 재설정에 6자리 코드를 쓰므로 대시보드에서 한 가지를 더 설정해야 한다:
**Authentication → Email Templates → Reset Password** 템플릿에 `{{ .Token }}`을 넣는다.
(기본 템플릿은 링크만 보내서 코드 입력칸에 넣을 값이 오지 않는다)

### 4. 첫 관리자 만들기 (관리자 모드를 쓸 때만)

관리자만 `admins`에 쓸 수 있는데 처음엔 관리자가 0명이라, 첫 한 명은 SQL로 넣어야 한다(닭과 달걀).
앱에서 회원가입을 마친 뒤 **SQL Editor**에서 한 번만 실행한다.

```sql
insert into admins (user_id)
select id from auth.users where email = '본인메일@example.com';
```

그 전까지는 관리자가 아무도 없어서 앱 어디에도 관리자 메뉴가 뜨지 않는다.
넣은 뒤에는 **로그아웃했다 다시 로그인**해야 한다 — 관리자 여부는 로그인할 때 한 번 확인한다.

### 5. 실행

```bash
npm start
```

Expo Go로 QR을 스캔하거나, 터미널에서 `a`(Android) / `i`(iOS) / `w`(웹)를 누른다.

## 테스트

두 층이 따로 있다. 위 설계 노트의 두 원칙이 각각 어디서 지켜지는지가 다르기 때문이다.

| | 무엇을 확인하나 | 실행 |
|---|---|---|
| `data/__tests__` (Jest) | **시간이 흐르면 무엇이 보이는가** — 예매 상태·보딩패스·스탬프·쿠폰 만료. 그리고 **파는 방식 판정**(설계 노트 3)과 관리자 입력 검증 | `npm test` |
| `supabase/tests` (pgTAP) | **서버가 무엇을 막고 어떻게 계산하는가** — 초과 판매, 쿠폰 중복 발급, 남의 예매 취소, 관리자 권한 | `supabase test db` |

**앞의 것**은 파생 함수가 전부 `now`를 인자로 받는 순수 함수라 가능하다. "자정이 지난 뒤에 앱을
켠 상황"을 기다리지 않고 시각을 넣어보면 된다.

**뒤의 것**은 진짜 Postgres가 있어야 한다. 돈과 권한이 걸린 판단은 전부 DB 함수 안에 있어서
(`create_booking` / `cancel_booking` / `issue_due_coupons`) 앱 테스트로는 닿지 않는다.
특히 이런 것들을 확인한다.

- 지난 회차로 예매해 **스탬프를 즉시 만들어낼 수 없다** (스탬프 9개 = 쿠폰 1장이라 곧 할인 발급 권한이다)
- 정원 2석짜리 회차를 2매로 채우면 **한 장도 더 팔지 않는다**
- `issue_due_coupons()`를 **몇 번을 불러도 쿠폰은 한 장뿐이다** (앱이 목록을 새로 받을 때마다 부른다)
- 남의 쿠폰·남의 예매는 **id를 알아도** 쓰거나 취소할 수 없다
- 관리자가 아니면 **공연을 등록·수정할 수 없다.** 관리자여도 공연 삭제는 권한 자체가 없어 끊긴다
- 전시에 회차가 생기면 **같은 공연이 회차형으로 바뀐다** — 기간 안의 날짜만으로는 살 수 없어진다

`supabase test db`는 로컬 DB가 필요해서 도커를 요구한다. 도커가 없으면 CI에서 돌아간다 —
`.github/workflows/ci.yml`의 `db-test` job이 매 PR마다 로컬 Supabase를 띄워 같은 테스트를 돌린다.

## 운영 노트

**카탈로그 날짜 밀기.** 시드의 공연 날짜는 고정 timestamp라 시간이 지나면 하나씩 지나가고,
결국 예매할 게 남지 않는다. 데모 전에 SQL Editor에서 한 번 돌리면 된다.

```sql
select shift_catalog_dates();
```

전체를 같은 일수만큼(요일이 유지되도록 7의 배수로) 밀어 "시드를 방금 넣은 상태"로 되돌린다.
돌려주는 값이 실제로 민 일수이고, **0이면 아직 밀 필요가 없다는 뜻이라 언제 돌려도 안전하다.**
예매 기록(`bookings.watched_at`)은 건드리지 않는다 — 이미 찍힌 스탬프가 뒤바뀌면 안 되기 때문이다.

공연과 회차를 함께 밀기 때문에 **관리자 모드로 등록한 공연도 같이 밀린다.** 시드가 아니라 직접
넣은 날짜를 그대로 두고 싶다면 이 함수를 돌리지 않는 편이 낫다.

## 아직 안 한 것

- **카탈로그 콘텐츠** — 시드 50건은 `description`이 비어 있고(상세에 "준비 중"만 뜬다)
  `poster_url`도 임시 이미지다. 저작권 문제로 실제 포스터를 넣을 수 없다.
  **채울 도구는 관리자 모드로 만들어 뒀고**, 내용을 아직 안 넣었을 뿐이다.
- **회차 반복 추가** — 회차를 하나씩 만든다. 시드가 공연당 9회차인 걸 보면
  "이 시각으로 7일간" 같은 방식이 있으면 손이 덜 간다.
- **지정석** — 좌석맵 없이 "자유석 + 인원" 모델이다.
- **관리자 감사 로그** — 누가 언제 무엇을 고쳤는지 남기지 않는다. 관리자가 한 명인 데모라 뺐다.
