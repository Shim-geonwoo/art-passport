# Art Passport — 데이터 구조 (최종)

> 문화예술 예매·아카이빙 앱의 데이터베이스 설계도.
> 저장소: Supabase (PostgreSQL)
> VS Code의 Claude에게 백엔드/DB를 만들라고 할 때 이 문서를 첨부하세요.

---

## 핵심 규칙 (확정)

- 여권 한 페이지 = 스탬프 **9칸** (3x3 그리드)
- 스탬프 칸에는 공연/전시 **포스터 이미지**가 들어감 (포스터 = 스탬프)
- 스탬프 9개를 채울 때마다 **쿠폰 1장** 발급
- 쿠폰 혜택: **다음 예매 10% 할인**
- 페이지는 계속 다음 장으로 이어짐 (여권처럼). 페이지 번호는 저장하지 않고
  스탬프 개수로 자동 계산 (예: 20개 -> 3페이지째, 2칸 채움)
- **`bookings.status`(예매완료/관람완료/취소)는 저장하지 않는다.** 저장하는 건 `is_cancelled` 하나뿐이고,
  나머지는 `now()`와 `watched_at`을 비교해서 조회할 때마다 계산한다. (아래 "상태 계산 규칙" 참고)
- **`stamps`는 별도 테이블로 두지 않는다.** 관람완료(파생) 상태인 `bookings`를 `watched_at` 오름차순으로
  정렬한 것 자체가 스탬프 목록이다. (별도 테이블을 두면 `watched_at`과 `stamped_at`이 사실상 같은 값을
  두 번 저장하게 되고, 취소 시점에 따라 서로 어긋날 위험이 생긴다.)

---

## 테이블 관계

- `auth.users` 1 : 1 `users`   (Supabase Auth가 인증을 관리, `users.id`가 `auth.users.id`를 참조)
- `users` 1 : N `bookings`     (한 회원이 여러 예매)
- `events` 1 : N `bookings`    (한 공연이 여러 예매를 받음)
- `users` 1 : N `coupons`      (한 회원이 여러 쿠폰)
- `coupons` 1 : 0~1 `bookings` (쿠폰 하나는 최대 한 번만 쓰임 — `bookings.used_coupon_id`로 연결)
- `events` 1 : N `event_schedules` (한 공연이 여러 회차) — **회차가 있으면 회차형, 없으면 기간형**
- `auth.users` 1 : 0~1 `admins` (관리자인 회원만 행을 갖는다)

## 테이블 상세

### users (회원)
| 칸 | 타입 | 설명 |
|---|---|---|
| id | uuid (PK, FK → auth.users.id) | 회원 고유번호 (Supabase Auth가 관리) |
| nickname | text | 닉네임 |
| profile_image | text, null 허용 | 프로필 사진 URL (Storage `avatars` 버킷의 공개 주소). 없으면 화면에서 사람 아이콘으로 대체 |
| created_at | timestamp | 가입일 |

### admins (관리자)
| 칸 | 타입 | 설명 |
|---|---|---|
| user_id | uuid (PK, FK → auth.users.id) | 관리자인 회원 |
| created_at | timestamp | 등록일 |

> **왜 `users`에 `is_admin` 칸을 두지 않았나**: 이 프로젝트에는 사용자가 자기 프로필 행을 직접
> 수정하는 정책이 이미 있다(닉네임·프로필 사진을 그렇게 바꾼다). 거기에 `is_admin`이 있으면
> **누구나 자기를 관리자로 승격시킬 수 있다.** 그래서 사용자가 손댈 수 없는 별도 표에 둔다.
>
> **두 겹으로 막았다.** 앱이 쓰는 역할(anon/authenticated)에서 권한을 회수하고(`revoke all`),
> RLS를 켜되 정책을 **하나도 만들지 않았다.** 이 표를 읽는 경로는 `is_admin()` 함수 하나뿐이다
> (`SECURITY DEFINER`라 표 주인 자격으로 돌아서 둘 다 통과한다).
>
> **첫 한 명은 SQL로 넣어야 한다.** 관리자만 이 표에 쓸 수 있는데 처음엔 관리자가 0명이라
> 닭과 달걀이 된다. 그 전까지는 앱 어디에도 관리자 메뉴가 뜨지 않는다.

### events (공연·전시)
| 칸 | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | 공연 고유번호 |
| title | text | 제목 |
| genre | text | 전시 / 클래식·무용 / 콘서트 / 연극 / 뮤지컬 |
| show_at | timestamp | 시작일. 카탈로그 정렬 기준이고, 기간형에서는 고를 수 있는 첫 날이기도 하다 |
| show_end_at | timestamp, null 허용 | **기간형으로 팔 때 쓰는 종료일.** 회차가 하나라도 있으면 회차형이라 이 값은 예매에 쓰이지 않는다 |
| price | int | 가격(원) |
| poster_url | text, null 허용 | 포스터 이미지 URL (스탬프에도 이 이미지 사용). 없으면 화면에서 카테고리색 박스로 대체 |
| description | text, null 허용 | 상세 소개글. 없으면 화면에서 "상세 내용이 준비 중이에요." 같은 빈 상태 문구로 대체 |
| venue_name | text | 공연장 이름 (지금은 글자로, 나중에 venue_id로 분리 가능) |
| is_hidden | boolean, 기본 false | 카탈로그에서 내렸는가. **삭제 대신 쓰는 칸** |
| created_at | timestamp | 등록일 |

> **공연은 지울 수 없다.** `bookings.event_id`가 `on delete restrict`라 예매가 한 건이라도 있으면
> DB가 거부하고, 그게 맞다 — 지워지면 이미 판 티켓의 예매 상세와 여권 스탬프가 가리킬 곳을 잃는다
> (스탬프는 관람완료 예매를 정렬한 것이라 `events`를 조인해서 그린다).
> 그래서 "내리기"는 삭제가 아니라 `is_hidden`으로 한다. 내려도 이미 예매한 사람의 보딩패스와
> 스탬프는 계속 보인다 — 그쪽은 이 칸을 보지 않기 때문이다.
>
> **내리면 새 예매는 서버가 막는다.** `create_booking`이 이 칸을 확인한다. 화면에서 목록에 안
> 뜨는 것만으로는 부족하다 — `events`의 select 정책은 누구나 열려 있어서, 상세를 열어둔 채로
> 공연이 내려간 사람은 그대로 결제까지 갈 수 있었다.
> 다만 **취소는 막지 않는다.** 내리기는 "앞으로 팔지 않겠다"는 뜻이지 "이미 판 것을 없던 일로
> 하겠다"는 뜻이 아니다. 이미 산 사람의 취소까지 막히면 환불 길이 끊긴다.

> **파는 방식은 플래그가 아니라 회차 유무가 정한다.**
>
> | 상태 | 파는 방식 | 예매 가능 여부 |
> |---|---|---|
> | 회차가 하나라도 있음 | 회차를 골라 산다 (회차마다 정원) | 안 지났고 자리도 남은 회차가 있는가 |
> | 회차 없음 + `show_end_at` 있음 | 기간 안에서 날짜를 고른다 (정원 없음) | `show_end_at ≥ 오늘` |
> | 둘 다 없음 | 아직 팔 수 없다 | 항상 불가 |
>
> `is_exhibition` 같은 칸을 두지 않은 이유: 칸으로 두면 "전시인데 회차가 있는" 모순된 조합을
> 만들 수 있고, 관리자가 칸과 회차를 손으로 맞춰야 한다. 이 방식에서는 회차를 만드는 행위 자체가
> 파는 방식을 정하고, 회차를 전부 지우면 기간형으로 돌아간다. 덕분에 시간지정 입장 전시(30분
> 단위로 인원을 끊어 받는 전시)가 별도 분기 없이 그냥 표현된다.
>
> 대신 이 판단이 네 곳에 흩어져 있어 **넷이 같은 순서로 갈라야 한다.** 하나라도 어긋나면 화면이
> "예매 가능"이라고 한 것을 서버가 거절해서, 누른 사람은 앱이 고장 난 줄 알게 된다.
>
> | 위치 | 하는 일 |
> |---|---|
> | `create_booking()` | 회차 id를 요구할지 관람 날짜를 요구할지 |
> | `isBookable()` (data/events.ts) | 목록·상세가 "예매 가능"을 보여줄지 |
> | `catalogVisibility()` (data/admin.ts) | 관리자에게 "왜 예매 탭에 안 보이는지" 뭐라고 답할지 |
> | 결제 화면 (booking/checkout.tsx) | 회차 고르기를 띄울지 달력을 띄울지 |
>
> 규칙은 `20260807103000_schedules_decide_type.sql`에 있고, 앱 쪽 판정은
> `data/__tests__/events.test.ts`가 못박는다.

### event_schedules (공연 회차)
| 칸 | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | 회차 고유번호 |
| event_id | uuid (FK → events.id) | 어느 공연의 회차인가 |
| starts_at | timestamp | 이 회차의 시작 일시 |
| capacity | int | 이 회차의 좌석 수(정원) |
| sold_count | int | 지금까지 팔린 매수. 트리거가 유지하는 **표시용 값** |
| created_at | timestamp | 등록일 |

> **정원을 events가 아니라 회차에 두는 이유**: 회차가 없으면 정원도 없으므로 "기간형=무제한"이
> 저절로 따라온다(`is_unlimited` 같은 플래그가 필요 없다). 또 같은 뮤지컬이라도 8/14 저녁과
> 8/15 낮은 좌석이 별개라, 정원의 단위는 공연이 아니라 회차가 맞다.
> 시간지정 입장 전시에 회차를 만들면 그 전시도 같은 방식으로 정원을 갖는다.
>
> **sold_count는 이 프로젝트에서 드문 "저장하는 파생값"이다.** 잔여석 = 정원 − 팔린 수인데
> 클라이언트는 RLS 때문에 남의 예매를 볼 수 없어 계산할 방법이 없다. 카탈로그를 부를 때 회차도
> 함께 받아오므로, 칸으로 두면 추가 왕복 없이 잔여석이 따라온다. 어긋나지 않도록 트리거는
> 값을 더하고 빼지 않고 **매번 처음부터 다시 센다**.
>
> **판매 가능 여부의 최종 판단은 sold_count를 믿지 않는다.** `create_booking`이 회차 행을
> `for update`로 잠근 뒤 직접 세어서 확인한다 — 마지막 한 자리를 두 사람이 동시에 사는 것을 막는다.

> **이 표에 행이 있는가가 곧 파는 방식이다** (위 events의 설명 참고). 보통은 공연만 회차를 갖고
> 전시는 기간 중 아무 날이나 가면 되어서 비어 있지만, 시간지정 입장 전시처럼 전시가 회차를
> 갖는 경우도 있다. `events.show_at`은 회차가 있을 때 보통 "첫 회차 일시"와 같은 값이다
> (어긋나도 막지는 않고, 관리자 회차 화면이 정렬이 어긋난다고 알려준다).
>
> **관람일은 둘 다 달력에서 고른다.** 회차형만 날짜 아래에서 회차를 한 번 더 고른다:
> - 회차형: 달력에서 **회차가 있는 날만** 고를 수 있고 → 그날의 시간(회차)을 고른다
>   → `watched_at` = 고른 회차의 `starts_at`
> - 기간형: 달력에서 기간 안의 날을 고른다 (모든 날 선택 가능)
>   → `watched_at` = 그날 **18:00**
>
> 기간형의 18:00은 "그날 관람을 마치는 시각"이라는 뜻이다. 이렇게 해야 오늘 예매해도 그날 하루는
> 보딩패스로 남아 있다가 저녁에 스탬프로 넘어간다(자정으로 잡으면 예매하자마자 스탬프가 된다).

### bookings (예매) — 앱의 심장
| 칸 | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | 예매 고유번호 |
| user_id | uuid (FK → users.id) | 예매한 회원 |
| event_id | uuid (FK → events.id) | 예매한 공연 |
| schedule_id | uuid (FK → event_schedules.id), null 허용 | 회차형에서 고른 회차. 기간형은 회차가 없어서 null |
| watched_at | timestamp | **이 예매의 실제 관람 시각.** 예매하는 시점에 확정한다(회차형은 고른 회차의 `starts_at`, 기간형은 고른 날짜의 18:00). 이후 바뀌지 않는다 — 나중에 그 공연이 회차형으로 바뀌어도 이미 판 표는 그대로다 |
| is_cancelled | boolean, 기본 false | 취소 여부. **저장하는 상태는 이것 하나뿐** |
| quantity | int, 기본 1 | 인원(자유석 매수) |
| used_coupon_id | uuid, null 허용 (FK → coupons.id) | 이 예매에 쓴 쿠폰. 있으면 10% 할인 적용, 그 쿠폰은 '사용완료' |
| original_price | int | 할인 전 금액 (예매 시점 event.price × quantity, 스냅샷) |
| total_price | int | 실제 결제금액 (할인 반영, 스냅샷) |
| created_at | timestamp | 예매한 시각 |

> `original_price`/`total_price`를 예매 시점에 스냅샷으로 저장하는 이유: `events.price`가 나중에 바뀌어도
> 과거 예매 금액이 따라 바뀌면 안 되기 때문이다.
>
> **상태(status) 계산 규칙** — 저장하지 않고 조회할 때마다 계산한다.
> 기준은 관람 **시각**이 아니라 관람 **일자**다. `stampAt` = 관람일 다음 날 00:00:
> ```
> is_cancelled = true   → '취소'
> now() < stampAt       → '예매완료'
> now() >= stampAt      → '관람완료'   (= 이 예매가 스탬프가 된다)
>
> 예) 관람일 7/29 19:30
>     7/29 23:00 → 아직 '예매완료' (지갑에 남아 있음)
>     7/30 00:00 → '관람완료'      (스탬프가 찍힘)
> ```
> 왜 시각이 아니라 날짜인가: 공연이 몇 시에 끝나는지를 저장하지 않는다(시작 시각뿐이다).
> 시작 시각을 기준으로 삼으면 아직 공연을 보고 있는 중에 티켓이 지갑에서 사라지고 스탬프가
> 찍힌다. "그날이 지나면"으로 잡으면 그런 일이 없고 "어제 본 공연"이라는 감각과도 맞는다.
>
> **취소 가능 여부는 이 status와 별개다.** 취소는 여전히 `now() < watched_at`(공연 시작 전)일 때만
> 가능하다 — 스탬프가 내일 찍힌다고 이미 시작한 공연을 취소할 수 있어야 하는 건 아니다.
> 그래서 화면은 status가 아니라 별도 파생값(`canCancel`)으로 취소 버튼을 띄운다.
> 이 둘을 같은 값으로 두면 "버튼은 보이는데 서버가 거절하는" 상태가 된다.
>
> 취소 판정이 시간 판정보다 우선이라, 관람일이 지난 뒤에도 취소된 예매는 계속 '취소'로 남는다.
> Supabase에서는 이 계산을 뷰(view)나 생성 컬럼(generated column)으로 만들어도 되고,
> 프론트에서 조회 시마다 계산해도 된다 — 어느 쪽이든 **크론으로 status를 미리 써넣지는 않는다**
> (취소 우선순위가 깨질 위험이 있다).

### coupons (쿠폰)
| 칸 | 타입 | 설명 |
|---|---|---|
| id | uuid (PK) | 쿠폰 고유번호 |
| user_id | uuid (FK → users.id) | 쿠폰 소유 회원 |
| benefit | text | 혜택 내용. 기본값: "다음 예매 10% 할인" |
| discount_rate | int | 할인율(%). 기본값: 10 |
| status | text | **사용가능 / 사용완료 (이 둘만 저장)** |
| expires_at | timestamp | 유효기간. 기본값: 발급일 + 90일 |
| issued_at | timestamp | 발급 시각 (스탬프 9개 채운 시점) |
| issued_at_stamp_order | int, null 허용 | 몇 번째 스탬프에서 발급됐는지(9, 18, 27...). 표시·디버깅용 |

> **'만료'는 저장하지 않는다.** 만료는 "언제까지인가"(`expires_at`)와 "지금이 언제인가"만 있으면
> 계산할 수 있어서, `bookings`가 `is_cancelled` 하나만 저장하고 나머지를 계산하는 것과 같은 꼴로 뒀다.
> 화면에 보이는 상태는 `data/coupons.ts`의 `couponStatus(coupon, now)`가 계산한다:
>
> | 조건 | 보이는 상태 |
> |---|---|
> | `status = '사용완료'` | 사용완료 (기간이 지나도 쓴 사실이 먼저다) |
> | 안 썼고 `expires_at ≤ now()` | 만료 |
> | 그 외 | 사용가능 |
>
> 이렇게 하면 **만료 처리 크론이 필요 없다** — 시각이 지나면 그 순간부터 만료로 보인다.
> 유효기간 90일 규칙은 `expires_at`의 기본값에 들어 있어서, 어느 경로로 발급하든 자동으로 붙는다.

## 핵심 기능이 데이터에서 작동하는 방식

**보딩패스 (예매하면 바로 표시)**
- `bookings`에서 `is_cancelled=false` 이고 `watched_at > now()`인 것(=상태가 '예매완료')을 전부 보딩패스로 표시.
- 예매를 마치는 순간 월렛에 들어오고, 관람일이 지나면(다음 날 00:00) 빠지면서 그대로 스탬프가 된다.
  ("예매하면 티켓이 지갑에 들어온다"는 앱 컨셉 그대로. 예전엔 관람 3일 전부터만 보여줬는데,
  예매하고 나서 한참 아무 데도 안 보이는 게 어색해서 조건을 없앴다.)
- 여러 개면 월렛처럼 겹쳐 쌓고, 위아래 스크롤로 넘겨봄 (카테고리 색으로 구분).
  관람일이 가까운 순으로 쌓여서 맨 앞이 곧 "다음에 갈 것"이 된다.
- **임박(오늘 포함 3일 이내)한 티켓에만 D-day 배지**를 붙여 강조한다.
  "월렛에 있나"(`isBoardingPass`)와 "임박한가"(`isSoon`)는 별개 값이다 — 한 값으로 겸하면
  석 달 뒤 공연에도 "관람이 임박했어요"가 뜨는 식으로 어긋난다.
- 표시할 티켓이 하나도 없으면 애플 월렛처럼 빈 화면 (안내 문구 없이 비움).

**자동 스탬프 (파생, 저장 안 함)**
- 별도 스탬프 생성 로직이 필요 없다. `is_cancelled=false` AND `watched_at ≤ now()`인 `bookings`를
  `watched_at` 오름차순 정렬한 것이 곧 스탬프 목록이다.
- 관람 시각이 지나는 순간, 같은 booking이 조회 시점에 자동으로 "보딩패스에서 빠지고" +
  "스탬프 목록에 들어오고" + "마이페이지 관람완료로 이동"한다. 별도 이벤트/크론이 필요 없다.

**쿠폰 발급**
- 한 회원의 스탬프(위에서 파생된 목록) 개수가 9의 배수가 될 때마다 `coupons`에 '사용가능' 쿠폰 1장을
  생성해야 한다. 이건 상태 계산과 달리 **실제로 행(row)을 만드는 일**이라 트리거가 필요하다:
  앱 진입 시 확인 로직 또는 Supabase 예약 함수(Edge Function + cron)로,
  "관람완료 스탬프 수가 9의 배수인데 아직 그 순번(`issued_at_stamp_order`)의 쿠폰이 없는 회원"을 찾아
  발급한다.

**티켓 검색**
- bookings를 event title / 날짜 / 장르로 검색해 내 티켓을 다시 꺼내봄.

**쿠폰 배너 (여권 페이지 완성 시)**
- 9칸을 채운 페이지에 "WE GOT A COUPON!" + 리워드함 이동 버튼을 띄운다.
- 배너를 띄울지도 **저장하지 않고 파생한다**: 그 페이지의 쿠폰(`issued_at_stamp_order` =
  페이지번호 × 9)이 아직 '사용가능'이면 띄우고, '사용완료'/'만료'면 내린다.
  화면 안의 state로 기억하면 앱을 껐다 켤 때 이미 받은 쿠폰의 배너가 다시 뜬다.

**여권 페이지 계산**
- 위에서 파생한 스탬프 총 개수 N개일 때:
  - 총 페이지 수 = ceil(N / 9)
  - 현재 페이지의 채워진 칸 = N % 9 (0이면 딱 맞게 채움)

## 쓰기 경로 (누가 무엇을 바꿀 수 있나)

앱(클라이언트)은 `bookings`·`coupons`를 **직접 쓰지 못한다.** RLS로 조회(select)만 열어두고,
쓰기는 아래 세 개의 DB 함수(SECURITY DEFINER)로만 한다. 금액·관람일·할인율처럼 **믿으면 안 되는 값은
전부 서버가 `events`/`coupons`를 다시 읽어 계산**하고, 클라이언트는 "무엇을·몇 매·어떤 쿠폰으로"만 말한다.

| 함수 | 하는 일 | 검증 |
|---|---|---|
| `create_booking(event_id, quantity, coupon_id, schedule_id, visit_date)` | 예매 1건 생성 + 쿠폰 '사용완료' 처리 (한 트랜잭션) | 로그인 여부, 인원 1~4, 고른 회차가 그 공연 것인지 / 고른 날짜가 전시 기간 안인지, 관람 시각이 안 지났는지, 쿠폰 본인 소유 + '사용가능' |
| `cancel_booking(booking_id)` | `is_cancelled` 켜기 + 쓴 쿠폰 '사용가능'으로 반환 | 본인 소유, 미취소, **관람 전(`watched_at > now()`)** |
| `issue_due_coupons()` | 스탬프 9개마다 쿠폰 발급 | 본인 스탬프 수를 서버가 다시 셈 |
| `delete_own_account()` | 회원 탈퇴 — `auth.users` 삭제 (프로필·예매·쿠폰이 연쇄 삭제) + Storage의 프로필 사진 삭제 | 인자를 받지 않고 `auth.uid()`로만 지우므로 남의 계정을 지목할 수 없다. 사진은 연쇄 삭제가 안 닿아서 함수가 직접 지운다 (실패해도 탈퇴는 진행) |

> 계정(`auth.users`)은 Supabase Auth가 관리하는 표라서 앱의 anon 키로는 지울 수 없다.
> service_role 키는 앱에 절대 넣지 않으므로(그 키 하나면 전 회원의 데이터를 다룰 수 있다),
> "본인 것만"이 박힌 함수를 서버에 두고 앱은 그것만 부른다.

> **왜 이렇게까지 하나**: 상태를 저장하지 않고 파생하는 설계(`watched_at` vs `now()`)라서,
> `watched_at`을 클라이언트가 정할 수 있으면 과거 시각을 적어 스탬프를 즉시 만들어낼 수 있다.
> 스탬프 9개 = 쿠폰 1장이므로 이건 곧 할인 발급 권한이 된다. 그래서 `bookings`에는 insert/update
> RLS 정책을 두지 않는다.
>
> **스탬프는 줄어들지 않는다**: `cancel_booking`은 관람 전 예매만 취소하고, 스탬프는 관람 시각이
> 지난 예매라서 둘은 겹치지 않는다. 즉 "쿠폰을 받은 뒤 예매를 취소해 스탬프만 되돌리는" 일은 불가능하다.

### 카탈로그 쓰기 (관리자) — 함수가 아니라 RLS 정책으로

`events`·`event_schedules`는 위와 달리 **앱이 직접 쓴다.** 서버 함수로 감싸지 않았다.

예매·쿠폰을 함수로 처리하는 이유는 **클라이언트가 보낸 값을 믿으면 안 되기 때문**이다. 금액과
관람 시각을 서버가 다시 읽어 계산해야 한다. 반면 공연 등록·수정은 **관리자가 곧 정보의 출처라
서버가 다시 계산할 원본이 없다.** 확인할 것은 "누가 하느냐" 하나뿐이고, 그건 정책이 하는 일이다.
함수로 감싸면 칸 수만큼 인자를 늘어놓은 껍데기가 될 뿐이다.

| 표 | insert | update | delete |
|---|---|---|---|
| `events` | 관리자만 | 관리자만 | **아무도 못 함** (정책도 권한도 없음) |
| `event_schedules` | 관리자만 | 관리자만 | 관리자만 |

> **권한(GRANT)과 정책(POLICY)은 다른 문이다.** 정책만 만들면 아무것도 안 된다 — 권한이 없으면
> 정책을 보기도 전에 permission denied로 끊긴다. 그래서 두 표에 `grant`를 함께 준다.
> 권한을 `authenticated` 전체에 여는 게 위험해 보이지만, 두 번째 문(정책)이 `is_admin()`을
> 요구하므로 통과하지 못한다. `admins` 표에서 두 문을 다 닫아둔 것과 짝이 되는 구조다.
>
> **공연 delete는 정책도 권한도 주지 않았다.** 둘 다 없으면 정책만 없을 때보다 확실하다 —
> 정책만 없으면 delete가 "조용히 0건"으로 끝나서 호출한 쪽은 성공한 줄 알지만,
> 권한이 없으면 예외로 끊겨 실수를 바로 알 수 있다.
>
> **회차 delete는 연다.** 잘못 만든 회차를 없애는 일은 실제로 필요하고, 이미 예매가 있으면
> `bookings.schedule_id`의 `on delete restrict`가 DB 차원에서 막아준다. 다만 **취소된 예매도 행은
> 남아서** 화면에 "판매 0"으로 보이는 회차도 삭제가 막힐 수 있다 — 관리 화면이 그 이유를 따로 알려준다.
>
> 앱에서 관리자 메뉴를 감추는 건 편의일 뿐이다. 관리자가 아닌 사람이 관리 화면 주소로 들어와도
> 목록은 보이지만(누구나 볼 수 있는 카탈로그다) 저장하려 하면 서버가 거절한다.

## 카탈로그 날짜 유지 (데모 수명)

시드의 공연·전시 날짜는 고정 timestamp라, 시간이 지나면 하나씩 지나가고 결국 예매 탭이 텅 빈다.
포트폴리오로 계속 보여줄 앱이라 **주기적으로 카탈로그를 앞으로 밀어줘야 한다.**

**돌리는 법** — Supabase 대시보드 → SQL Editor:

```sql
select shift_catalog_dates();
```

돌려주는 숫자가 실제로 민 일수다. **0이면 아직 밀 필요가 없다는 뜻이라, 언제 돌려도 안전하다.**

| | |
|---|---|
| **기준** | "가장 이른 이벤트는 오늘로부터 70일 전에 시작한다"를 유지한다. 시드를 만든 날의 모양 그대로다 |
| **단위** | 7의 배수로만 민다 — 금요일 공연이 계속 금요일이도록 |
| **대상** | `events.show_at` / `show_end_at`, `event_schedules.starts_at` |
| **제외** | `bookings`. `watched_at`은 "그때 산 관람 시각"의 스냅샷이라 고치면 이미 찍힌 스탬프와 지난 예매가 뒤바뀐다 |

> 그 결과 오래된 예매의 `schedule_id`가 가리키는 회차는 시각이 달라지는데, 화면은 어디서도
> 그 회차 시각을 쓰지 않고 `watched_at`만 보므로 문제되지 않는다.
>
> 매번 손으로 돌리는 게 번거로우면 `pg_cron`으로 월 1회 호출하게 걸 수 있다.
> 지금은 "언제 무엇이 바뀌는지 눈에 보이도록" 일부러 수동으로 뒀다.

## 파일 저장소 (Supabase Storage)

### avatars 버킷 — 프로필 사진
- **경로 규칙**: `{user_id}/avatar.jpg` — 맨 앞 폴더가 회원 id다.
  정책에서 `(storage.foldername(name))[1] = auth.uid()::text` 하나로 "본인 폴더인가"를 확인한다.
- **공개 버킷**이다. 프로필 사진은 감출 정보가 아니고, 공개면 이미지 주소를 그대로 쓸 수 있어
  화면에서 서명된 URL을 매번 발급받지 않아도 된다.
- **읽기는 누구나, 쓰기·삭제는 본인 폴더만.**
- 회원당 파일 하나를 덮어쓴다(upsert). 바꿀 때마다 새 파일을 만들면 예전 사진이 계속 쌓인다.
  대신 주소가 늘 같아 캐시에 옛 사진이 남을 수 있어서, `users.profile_image`에 저장하는 주소
  끝에 `?v={시각}`을 붙인다.

### posters 버킷 — 공연 포스터

`avatars`를 그대로 본떴다. 다른 것은 조건 하나다 — `avatars`는 "본인 폴더인가"를 보고,
`posters`는 "관리자인가"(`is_admin()`)를 본다.

- **경로 규칙**: `{event_id}/poster.jpg` — 공연 하나에 포스터 한 장이라 경로가 곧 그 공연의 자리다.
- **공개 버킷**이다. 포스터는 예매 카탈로그의 일부라 로그인 전에도 보여야 한다
  (`events` 조회가 비로그인에도 열려 있는 것과 같은 이유).
- **읽기는 누구나, 올리기·바꾸기·지우기는 관리자만.**
- 같은 경로에 덮어쓰고(upsert) 주소 끝에 `?v={시각}`을 붙이는 것도 `avatars`와 같다.
- 공연 자체는 지울 수 없지만 **포스터는 지울 수 있다.** 잘못 올린 이미지를 내리는 건 흔한 일이고,
  지워도 카탈로그는 카테고리 색 박스로 대체해서 계속 보인다.
